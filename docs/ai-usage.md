# AI allowances

Super Admin → AI usage and access → Per-user AI allowances lets a verified super admin select any teacher or learner, then save a default, custom whole-number daily limit, or unlimited for each AI feature. Zero disables generation for that feature. Limits reset at 00:00 UTC. Saving changes affects the next new request; work already running may finish. Conflicting saves require reloading the latest settings.

All verified super admins, including the owner and protected registry members, bypass application generation-count and monthly spending caps. Their lesson/help cost accounting is separate from ordinary users, so their unrestricted use does not consume the ordinary shared budget. Authentication, access permissions, provider availability, input/file bounds and preventing duplicate concurrent jobs remain in place.

Ordinary users retain existing feature permissions and the existing shared lesson/help service budgets. Their per-feature daily settings replace the old service-specific daily/global creation counters. Failed attempts after reservation count; validation failures before reservation do not. Recovering an existing job, polling, playing or saving output does not count again. An internal repair pass does not consume a second logical use. Lesson images and recordings each count as a new prepared asset, including an explicit retry.

The server owns `aiAllowances/{uid}` and `aiFeatureUsage/{uid}/days/{UTC-day}`. Clients cannot write either. Only the `adminAiUsage` callable may save policy after checking the verified, non-impersonated protected super-admin identity. Limits are checked and counted in the same Firestore transaction as each new job reservation. Speech and realtime sessions count against the requesting user, including learners, rather than an unrelated class-owner speech quota. Usage shown is tracked from deployment of this feature; previous-generation counters are retained as legacy accounting.

`functions/ai/features.js` is the authoritative catalog. A future paid AI entry point must call `chargeFeature` inside its job reservation transaction, after all reads and idempotency checks and before writes, or `reserveFeature` for a synchronous request without a job. Unknown feature IDs fail closed. Resolve privilege with `usageContext`; never trust profile roles or client flags. Background jobs resolve the actual Firebase Auth identity and current protected registry before reservation.

Verification: `node --test test/ai/feature-usage.test.mjs`; Firestore and Auth emulators with `node test/ai/feature-usage-integration.mjs`; browser journey `AI usage` in `test/smoke.mjs --a11y`. Integration and browser fixtures mock paid providers; they do not establish live provider generation. Deployment must be followed by testing published controls and a real usable result before claiming live generation works.
